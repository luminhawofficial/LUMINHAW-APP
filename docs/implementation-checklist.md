## Screen checklist

| Screen / flow | Current state |
| --- | --- |
| Intro and onboarding | Present; local completion preference is saved. |
| Welcome | Login and account creation remain; the preview-entry button was removed. |
| Login | Supabase password sign-in and client validation are present. |
| Sign up | Supabase account creation and client validation are present; verification and resend links target the configured web origin or Android auth callback. Email delivery and allowed redirect URLs require project configuration. |
| Email verification | Resend flow is present; delivery and redirect configuration are external. |
| Password reset | Reset requests use a dedicated Android callback and Supabase PKCE recovery; only the verified recovery session can update the password. The recovery email template includes a browser fallback for users without the app. Configure the production web Site URL, redirect allowlist, and recovery template as described in the README, then verify on a configured project/device. |
| Home and five-tab navigation | Screens and navigation are present. |
| Plant library | No bundled sample records; authenticated search invokes the `plant-catalog` Supabase function with `{ "q": "<plant name>" }`, filters accepted species, and deduplicates by accepted taxon ID. Perenual is tried first, Trefle is the next configured provider, and public GBIF is the final fallback. GBIF result photos are retrieved from matching backbone taxon occurrence records; only HTTPS photos with CC0 or CC BY licenses are returned. Available creator, license, and source-reference metadata is shown on plant details. Missing/unusable images retain the placeholder. GBIF occurrence images are cached for six hours (empty/error results for two minutes) per warm function instance; searches look up photos for all returned species with up to three concurrent requests. Verify the deployed function with a signed-in request before release. |
| Plant scanner | Camera/gallery selection, explicit photo-processing consent, image validation, authenticated Plant.ID request with PlantNet fallback, and per-user scan persistence are implemented. Scan results also look up Tagalog (tgl/fil) and Cebuano/Bisaya (ceb) vernacular names from GBIF when the accepted species match is sufficiently confident; missing translations are shown as unavailable rather than guessed. Test with rotated provider credentials and deployed Supabase configuration. |
| Scan result and history | Real response parsing and per-user Supabase scan status/result persistence are implemented; verify deployed migration/RLS/function and recovery behavior against a non-production project. |
| My Garden | Signed-out use remains device-local. Signed-in users with verified email read and write owner-scoped Supabase plants. Care activities and growth entries require an active Premium entitlement in both the UI and RLS policies. Legacy device-only data is intentionally not auto-migrated because it has no account ownership metadata. Verify RLS, auth-switch behavior, and cloud CRUD against a non-production project. |
| Care guide | The authenticated `plant-care` Edge Function exact-matches the selected scientific name in Perenual, returns only provider-supplied watering, sunlight, soil, hardiness, maintenance, and pest fields, and caches results for 24 hours per warm instance. Detailed guides are Premium-gated in the UI and server. Configure `PERENUAL_API_KEY`, deploy the function, and verify provider licensing and responses before release. |
| Plant detail enrichment | The authenticated `plant-enrich` Edge Function returns basic names, taxonomy, description, and basic-care fields to Free accounts. Advanced provider-sourced biology/care and AI-generated details require a server-verified Premium entitlement. Free and Premium cache entries are separate; enrichment cache version 6 refreshes previous schemas. Configure `TREFLE_API_KEY`, deploy the function, and verify provider terms and plan responses before release. |
| Growth tracker | Care logs and observations use owner-scoped Supabase tables for signed-in users with verified email and an active Premium entitlement; RLS enforces the entitlement for reads and writes. Signed-out data remains device-local. The tracker and add-entry screen are Premium-gated in the UI. Its guidance uses planting date, growth stage, and recent care history; completed tasks and notes are stored on-device per account and are not cloud-synced. No legacy local data is auto-migrated. Verify cloud CRUD and access controls against a non-production project. |
| Notifications | Opt-in local notifications schedule daily 9:00 AM watering checks and stage-based fertilizer reminders for saved garden plants, rescheduling after plant/care changes. The notification center reads published app-wide announcements (updates, maintenance, features, general account notices) from `system_announcements`. Apply the migration before release and publish only non-sensitive app-wide content through a trusted administrative process. Test Android notification permission, scheduling, device reboot restore, and announcement expiry against a non-production project. |
| Health checker | Camera/gallery selection, explicit photo consent, image validation, private per-user photo upload, authenticated Edge Function invocation, provider result parsing, and owner-scoped assessment persistence are implemented. The server verifies Premium entitlement and rate limits requests; purchase setup, deployed-provider verification, and live signed-in testing remain outstanding. |
| LUMIN AI | Assistant screen and Gemini Edge Function require verified authentication. Basic accounts are limited to 10 requests per UTC day, including one automatic care suggestion per plant per UTC day; Premium accounts can receive up to four suggestions per plant per UTC day. Limits are enforced server-side. The server prompt restricts answers to botany and plant care, requires uncertainty and toxicity guidance for identifications, and warns against foraging decisions. Chat and care suggestions send text only; image analysis must use the plant scanner. Client and server cap conversation context to the latest valid messages; oversized current messages are rejected before the request. Verify Basic and Premium limits against a non-production project. |
| Premium and payment | Client reads server-managed entitlement rows; refreshes discard stale responses across account changes and surface verification errors while failing closed. Manual payment collection remains disabled pending merchant approval and configuration; Google Play Billing and purchase verification are not implemented. |
| Manual Premium payments | Email-only approval tokens, private receipt storage, signed-in payment requests, strict OCR matching, and transactional entitlement activation are implemented locally. The email action requires a one-time token and explicit confirmation; both plans remain disabled. The migration and Edge Function changes are not deployed. OCR cannot independently establish receipt authenticity or detect blur/cropping reliably, and no GCash API/webhook is implemented. |
| Profile and edit profile | Supabase display-name update and profile-photo upload are implemented. Verified users upload their own JPEG, PNG, or WebP photo to the private `plant-photos` bucket; the app stores the owner-scoped `avatar_path`, displays it with a signed URL, and removes the previous photo after replacement. Verify storage policies and upload/display/delete behavior against a deployed non-production project. |
| Account deletion | Confirmation is followed by password reauthentication; the Edge Function requires a recently authenticated JWT, cleans up the user's private plant and payment photos, then deletes the account. Storage cleanup and reauthentication need deployment and non-production verification. |
| Privacy and usage | In-app privacy and account disclosures now reflect verified-account garden/growth sync and private health-photo storage. A reviewed, publicly hosted policy, verified retention details, and publisher contact details are still required. |

## Current release blockers

- No supplied set of five screenshots for visual comparison.
- Plant provider credentials must be stored as Supabase Edge Function secrets, not in the app or source control: `PLANT_ID_API_KEY`, `PLANTNET_API_KEY`, `PERENUAL_API_KEY`, and `TREFLE_API_KEY`. Plant.ID and PlantNet provide identification; Perenual and Trefle provide catalog/enrichment data. The plant catalog tries configured providers in Perenual, Trefle, then GBIF order. The updated image lookup requires deploying the `plant-catalog` function and verifying a signed-in search. GBIF images without HTTPS URLs, creator attribution when required, or an allowed CC0/CC BY license are intentionally omitted. Review provider terms before release. Health analysis requires a verified Premium entitlement, a configured `PLANT_ID_API_KEY`, deployed function/migrations, and signed-in testing; the result is advisory and not a confirmed diagnosis.
- Supabase migrations and Edge Functions need deployment and remote configuration. Provider credentials and email delivery are not supplied. Account deletion now requires password reauthentication and a JWT with `auth_time` less than five minutes old.
- Garden and journal cloud sync is implemented against the existing owner-scoped schema but has not been tested against a deployed Supabase project. Existing device-only records remain local and are not automatically attributed to an account.
- Species-specific care data needs an active Perenual API key; GBIF-only catalog matches without an exact Perenual species record will show an unavailable state rather than invented guidance.
- GCash merchant receiving approval, QR uploads, payment email/OCR secrets, the email-approval migration and function deployment, and live non-production verification are outstanding. Both plans remain disabled until these are complete and the owner explicitly authorizes activation. Google Play Billing and trusted automated gateway processing are not implemented.
- A production privacy policy URL, publisher contact, and legal/data-safety review are not supplied.
- Release signing properties and the upload keystore are not present. Signed APK/AAB generation is therefore blocked; the owner must create and protect the upload keystore and local `android/key.properties`.
- NDK `28.2.13676358` is installed, and `flutter build apk --debug` completed successfully in this environment. A signed release build still requires the signing files above.
- Authentication, scan, database, subscription, and release flows have not been verified against production providers or Google Play.
